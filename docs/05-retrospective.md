## 最难的问题

1. **怎样让“动态决策”真正由模型做，同时又有可靠的护栏。** 最容易写成“检索到两份文档 → 判冲突”这样的固定分支，但那样就不算 ReAct。最后的划分是：结束状态和每一步动作都由模型选择；代码只做三件与业务无关的事：执行工具、限制预算、校验证据（闸门）。闸门不判断答案对不对，只判断“引用的原文是否真实存在、是否真的被读过”。这样，C02 和 C08 的路径差异完全来自工具返回内容的不同。
2. **合成数据要能区分“可查证的冲突”和“不可查证的冲突”。** D01/D02 刻意不写适用范围和优先级（不可查证，应请求确认），D03/D07 则在元数据和正文中都写明替代关系（可查证，应按新版回答）。数据设计决定了测试能否区分两种正确行为。
3. **评测本身也会出错。** C10 的断言先后两次误判：先是把“警示注入文本”当成“执行了注入”，后来又把“有。……带有星剪水印”的第一句只截成了“有”。如果只看通过率，要么得出模型不安全的错误结论，要么被诱导去改提示词迎合断言。最后的做法是：人工核对原文 → 修正断言 → 用同一份输出重新判定 → 把过程写进文档。
4. **DeepSeek 思考模式的协议细节。** 带 tools 时，每一轮的 `reasoning_content` 都必须回传，因此不能随意伪造 assistant 历史消息。对话历史因此改为放在 user 消息中，以文本形式传入。

## 学到的东西

- 状态栏（每轮临时追加、不进入历史）是一种很便宜的上下文工程手段：模型能看到证据台账和预算。C06a 的最后一步，模型给出的依据就是“预算即将耗尽，直接提交答案”。不过本次没有做开关状态栏的对照实验，它对效果的具体贡献还没有量化。
- 层次型知识库加上 `outline` 元数据，让“查证冲突”变成了一个具体的工具动作，而不是寄希望于模型从片段里自己推断。
- 工具失败时“不自动重试、把错误分类和建议交给模型”，换来了 C06a 中“换工具绕行”的行为。这是固定重试逻辑做不到的。
- 真实模型的问题往往不在主路径上，而在细节里（C05 的无依据补充、C06a 的冗余探索）。这些只有逐条读 trace 才能发现。
